# Discord API documentation review

Local implementation and verification: **2026-11-05**. REST and Gateway remain
**v10**; OAuth authorization remains unversioned. No runtime dependency is added.

Reviewed the official documentation changes from discovery revision
[`37148620d2324292b76047541d5f8331f81ea77a`](https://github.com/discord/discord-api-docs/tree/37148620d2324292b76047541d5f8331f81ea77a)
through main revision
[`da52492ced82d375981c46618cc3e182daada9a2`](https://github.com/discord/discord-api-docs/tree/da52492ced82d375981c46618cc3e182daada9a2).
The [complete upstream comparison](https://github.com/discord/discord-api-docs/compare/37148620d2324292b76047541d5f8331f81ea77a...da52492ced82d375981c46618cc3e182daada9a2)
includes protocol changes, SDK-only guidance and documentation-site maintenance.
Original discovery membership and historical evidence remain separate from this review.

## Implemented changes

- **Computed permissions:** Previously no typed server-calculation routes existed.
  `GuildEndpoints.memberPermissions` and `rolePermissions`, plus
  `ChannelEndpoints.memberPermissions` and `rolePermissions`, now return
  `ComputedPermissions`. Its required decimal-string `permissions` preserves
  arbitrary width, leading zeroes and unknown response fields. Guild calculations
  combine the target's applicable roles with `@everyone`; a role calculation
  excludes other roles and member restrictions. Channel calculations apply
  overwrites, using the parent for threads. Optional `implicit` defaults to nil,
  omitting the query and retaining the server's true default; explicit true/false
  are supported. Member masking does not apply to bot targets. Channel routes
  require VIEW_CHANNEL and additionally CONNECT for voice/stage channels. All four
  are safe bot-authenticated GETs with HTTP 200, scoped coalescing by default and
  no completed TTL cache unless requested. [Current Guild](https://docs.discord.com/developers/resources/guild#get-guild-member-permissions)
  and [Channel contracts](https://docs.discord.com/developers/resources/channel#get-channel-member-permissions);
  [pinned addition](https://github.com/discord/discord-api-docs/commit/9d2128bb8301e7d9f239ff259f2ee41cf4d73c70).
- **Content scanning:** Attachment/embed response bits previously survived only
  as raw flags. `MessageAttachmentFlags` and `MessageEmbedFlags` now name explicit,
  gore and self-harm bits 4, 6 and 7. `UnfurledMediaItem.contentScanMetadata`
  projects optional response-only `UnfurledMediaContentScanMetadata`, whose required
  flags name the corresponding bits 0, 1 and 2. Unknown fields and bits remain
  exact. Scanning may complete in a later Message Update; absent metadata does
  not imply a completed scan. Interaction-resolved uploads lack these flags until
  sent in a message. Outgoing components still reject response-only metadata.
  [Current attachment flags](https://docs.discord.com/developers/resources/message#attachment-object-attachment-flags),
  [component media](https://docs.discord.com/developers/components/reference#unfurled-media-item)
  and [pinned change](https://github.com/discord/discord-api-docs/commit/2b434c56eca46b61461bf5578499dd7810e2f6af).
- **Forum/media starters:** `ForumThreadStart` previously rejected Components V2.
  It now accepts IS_COMPONENTS_V2 while retaining shared message validation that
  excludes traditional content, embeds and stickers in that mode. Other unsupported
  message features remain rejected. [Current contract](https://docs.discord.com/developers/resources/channel#start-thread-in-forum-or-media-channel)
  and [pinned change](https://github.com/discord/discord-api-docs/commit/9f67300deca664315de53d399ddede55e40c626d).
- **Audit and channel ordering:** `AuditLogEvent` now recognizes
  `channelPositionUpdate` (16) and `rolePositionUpdate` (33), previously unknown raw
  values. Their optional `count` remains an exact wire string. Channel-position
  descriptors now accept an audit reason. Successive message deletes/bulk deletes,
  member disconnects/moves and channel/role reorders can merge into an entry,
  retaining only the first reason and emitting no further Gateway event for the
  merged update. [Current audit contract](https://docs.discord.com/developers/resources/audit-log#audit-log-entry-object-audit-log-entry-merging)
  and [pinned change](https://github.com/discord/discord-api-docs/commit/ee16658e2304c3b44b2c652f4cae0a4363c4c081).
- **Removed request fields:** Single-message deletion no longer emits an
  X-Audit-Log-Reason header. Channel-position requests no longer encode `flags`.
  [Delete Message](https://docs.discord.com/developers/resources/message#delete-message),
  [Modify Guild Channel Positions](https://docs.discord.com/developers/resources/guild#modify-guild-channel-positions)
  and their pinned [deletion](https://github.com/discord/discord-api-docs/commit/3a45efdd573ac6a786752e3dd7b9f8ba44d3d5ef)
  and [position](https://github.com/discord/discord-api-docs/commit/c989436e97b194350ec4712aec77207c2f9f2332)
  corrections establish the current outgoing contract.

## Existing behavior confirmed

`OAuthAuthorizationFlow` already requires exact state, redirect and Discord issuer
for code and implicit callbacks before exposing credentials. The reference now
explicitly documents `iss`, authorization-server metadata, OpenID discovery and
the preference for code authorization with PKCE over implicit grants. The fixed
issuer and S256 default remain unchanged; no discovery fetch is added.
[Current OAuth reference](https://docs.discord.com/developers/topics/oauth2#issuer-identification)
and [pinned change](https://github.com/discord/discord-api-docs/commit/f7416a2cf165455f72a31f5ea4e671a4f047f2f7).

The written [Application Role Connection table](https://docs.discord.com/developers/resources/user#application-role-connection-object)
now confirms existing optional platform name, username and metadata projections.
Names remain nullable; metadata absence remains distinct from an empty map.
`PermissionResolver` already retains SET_VOICE_CHANNEL_STATUS when CONNECT is
implicitly denied, matching the [connected-user clarification](https://docs.discord.com/developers/resources/channel#set-voice-channel-status).
Guild availability already preserves absent/false/true values: true means currently
unavailable, and a later Guild Create restores availability to the session. Comments
now follow the [current Guild Delete wording](https://docs.discord.com/developers/events/gateway-events#guild-delete)
without attributing loss of access to a particular cause.

Webhook PING still returns an empty HTTP 204. Its retained application/json header
remains compatible, while comments no longer claim that the header is required.
The [webhook reference](https://docs.discord.com/developers/events/webhook-events)
removed that requirement; response behavior and durable event admission are unchanged.

## Native SDK guidance and editorial changes

The Social SDK guides clarify [refresh/status callbacks](https://docs.discord.com/developers/discord-social-sdk/development-guides/account-linking-with-discord),
the [180-second cold-launch join window and provisional-account invites](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-game-invites),
and [lobby membership/connection/availability callbacks](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-lobbies).
Registering native join callbacks before connecting, repeated lobby-created events
after recovery, and lobby-deleted events on access loss/outage do not define new
REST or RPC wire contracts. Existing native-only blockers and public-equivalent
classifications remain; REST snapshots do not provide those callback guarantees.
The web account-linking guide's issuer check is already enforced by OAuth.

Privileged-intent guides only fix slash-command links. The Game Stats Widget
overview adds a video. The YouTube snippet, site CSS, lint invocation, script
allowlist and dependency-lock updates concern the documentation site and require
no DiscordKit runtime changes. Redundant optional markers removed from the thread
PATCH table do not make its fields required; existing partial-update semantics remain.

## Migration and chronology

The new permission endpoints, scan projections and audit cases are additive.
Existing raw unknown flags and action values remain readable. Use
`MessageEndpoints.delete(channelID:messageID:)`; its deprecated explicit-auditReason
overload ignores the supplied argument, including values formerly rejected by
audit-reason validation, and emits no header. Bulk deletion retains audit support.
Use the channel-position initializer without `flags`. Its deprecated compatibility
overload accepts only `.absent`; null and supplied values now throw before I/O.
Move flag updates to `ChannelModify` through `ChannelEndpoints.modify`.

Official change-log announcements date issuer responses to **2026-10-14**, content
scanning to **2026-10-28**, audit position actions and the voice-status exception to
**2026-10-29**, and computed permissions to **2026-10-30**. Separate effective dates
remain unknown. Guide dates and repository publication dates are evidence of
documentation publication, not inferred protocol activation dates.
The existing **2026-11-16** mandatory channel-obfuscation transition is unchanged
and remains future on this verification date. No live Discord, native SDK,
cross-platform runtime or production-capacity qualification is established.
